- **[Fix82] Persistencia y visibilidad de las tres notas (Revisor Final + Holístico + Beta) tras cada iteración del loop holístico+beta (v8)**: Queja del usuario: "cuando se reevalúa el manuscrito tras cada reedición, se debe mostrar la nueva nota del editor final y también la de los lectores holístico y beta". Diagnóstico: tras Fix81 cada iteración del loop persistía `holisticScore`/`betaScore` y reescribía `finalScore` vía `recalculateFinalScoreAfterEdits`, pero (a) el texto íntegro del informe holístico se descartaba (solo quedaba la nota /10), (b) ninguna escritura de `finalScore` registraba marca temporal, así que el usuario veía cambiar números sin saber cuáles eran nuevos ni podía leer el diagnóstico que los justificaba. Implementación: **(1) Schema** (`shared/schema.ts:108,160`): nuevas columnas `projects.finalScoreAt timestamp`, `projects.lastHolisticNotes text` (truncado a 24k), `projects.lastHolisticNotesAt timestamp`. **(2) Migración idempotente** (`server/db.ts:21-29`): tres `ALTER TABLE IF NOT EXISTS` añadidos al array `SCHEMA_PATCHES` que se aplica en cada boot — patrón heredado de Fix79 que evita el bloqueo interactivo de `drizzle-kit push`. **(3) Backend persistencia holístico** (`server/orchestrator.ts:5876-5894`): `_runHolisticReview` ahora persiste **siempre** `lastHolisticNotes`+`lastHolisticNotesAt` (incluso si el parser de `puntuacion_holistica` no encuentra número), y solo opcionalmente `holisticScore`+`holisticScoreAt` cuando `typeof result.score === "number"`. Mantiene la semántica de Fix75 de no pisar el score previo cuando no hay parseable, pero deja el informe del cuerpo visible aunque la nota falle. **(4) Backend persistencia final** (`server/orchestrator.ts:4203-4211, 4585, 5500-5505, 8198-8206, 11644-11648`): los 5 sites de update de `finalScore` ahora también escriben `finalScoreAt: new Date()` — el principal (`recalculateFinalScoreAfterEdits` L8198) es el que dispara el loop Fix81 tras `applyEditorialNotes`. **(5) UI dashboard** (`client/src/pages/dashboard.tsx:1289-1408`): el bloque "Notas adicionales de los lectores" (grid de 2 score-cards) se reemplaza por "Notas tras la última reedición" — grid de 3 note-cards (Final / Holístico / Beta) que muestra para cada una: score con color (verde≥9, amarillo≥7, rojo<7), timestamp "hace X min/h/d", y un `<details>/<summary>` colapsable con el cuerpo del informe (24k chars máx, scroll vertical 256px). La card del Final usa `finalReviewResult.reason` o las primeras 5 issues como preview de texto. Helper `fmtAgo` null-safe. **(6) Edge case post-code-review**: la card del Holístico usa `lastHolisticNotesAt ?? holisticScoreAt` (no al revés) porque las notas se persisten siempre y el score no — si una iteración devuelve informe nuevo sin score parseable, queremos que la card siga reflejando "hace X" basado en la frescura del informe, no del score viejo. Idéntico para Beta. Trade-offs: el truncado a 24k chars es lo mismo que Fix38 para `lastBetaNotes` — coherente, pero informes muy largos (> 24k) pierden el final. Solo se persiste el ÚLTIMO informe; no hay historial de iteraciones — si el usuario quiere ver la evolución necesita mirar el activity log que sí registra cada iter con `[Fix81] Iter X: Holístico=Y (Δ), Beta=Z (Δ)`. El `finalScoreAt` queda null para proyectos antiguos hasta que se reevalúen — la UI lo trata como null-safe ("hace X" no aparece). La reedit page (`client/src/pages/reedit.tsx`) tiene su propia tabla `reeditProjects` con campos paralelos (`holisticScore`/`betaScore` en L708/710 del schema); este Fix solo cubre la tabla `projects` y el dashboard principal — si el usuario también quiere ver las notas en la página de reediciones, hace falta extender el schema de reedit (paralelo, pendiente).

- **[Fix81] Pipeline post-generación rediseñado: target DUAL ESTRICTO Beta≥9 AND Holístico≥8, ortotipográfica al FINAL, snapshot+regresión y anti-stall robusto (v8)**: Queja del usuario: el sistema casi nunca alcanza puntuaciones altas porque la corrección ortotipográfica corría ANTES del loop holístico+beta, el loop solo exigía Beta≥9 ignorando el Holístico, abortaba con 1 sola iteración estancada, y no había snapshot. Implementación: **(A) Ortotipográfica movida al final** (`server/orchestrator.ts:10954-10962` reemplaza llamada en `finalizeCompletedProject`): antes corría ANTES del loop y cada reescritura posterior la destruía + el Beta penalizaba prosa sin pulir. Ahora se ejecuta SOLO al alcanzar el target dual, vía `runOrthotypographicPassAndUpdate` (`server/orchestrator.ts:7779-7798`). **(B) Target dual estricto** en `runAutoHolisticReviewLoop` (`server/orchestrator.ts:7639-7654`): condición de salida cambiada de `betaScore >= TARGET_BETA_SCORE` (ignoraba holístico) a `betaScore >= 9 AND holisticScore >= 8`. Sin fallback: si tras MAX_ITERATIONS no se alcanza, persiste notas SIN marcar aprobado y SIN ejecutar ortotipográfica. **(C) MAX_ITERATIONS 3→8** (`server/orchestrator.ts:7425`) configurado por el usuario; anti-stall reescrito (`server/orchestrator.ts:7695-7716`): antes `stalledSameScore >= 1` (1 sola iter con mismo Beta abortaba ignorando si Holístico mejoraba); ahora `stalledIterations >= 2` AND ningún score subió (deltaB ≤ 0 AND deltaH ≤ 0) en 2 iters consecutivas. **(D) Snapshot+regresión estilo Fix39** (`server/orchestrator.ts:7434-7452` helpers `snapshotManuscript` y `restoreSnapshot`; `server/orchestrator.ts:7569-7611` lógica): se mantiene `bestSnapshot` con la mejor combinación (beta+holístico) vista. Si la combinación actual cae ≥ `REGRESSION_THRESHOLD` (1.0) respecto al mejor, se restauran los capítulos del snapshot y se aborta el loop preservando la mejor versión; si el snapshot ya cumplía target dual se ejecuta la ortotipográfica final, si no se persiste para revisión manual. **(E) Inyección de Biblia de Serie + Hitos/Hilos** en aplicación de notas: verificado que `applyEditorialNotes` (`server/orchestrator.ts:8788`) llama a `rewriteChapterForQA` (`server/orchestrator.ts:12680`) que **internamente** ya carga `seriesUnifiedWorldBibleStr` (L12703/12706, L13470/13518) y `seriesMilestonesBlockStr` (L13471) gracias a Fix78+Fix80; no requiere edición adicional. **(F) Logging mejorado** (`server/orchestrator.ts:7559-7562`): cada iteración loguea `Holístico=X (Δ), Beta=Y (Δ)` con deltas vs iter anterior y la decisión tomada (target alcanzado / regresión / estancamiento / max iter / aplicando notas). Mensajes [Fix77]→[Fix81] actualizados en todo el loop. **Coverage adicional**: `runAutoBetaLoop` (legacy, flag `autoBetaLoop`) también llama a `runOrthotypographicPassAndUpdate` al aprobar (`server/orchestrator.ts:11195-11197` rama sin notas + `server/orchestrator.ts:11239-11243` rama approved); antes la ortotipográfica solo dependía de `finalizeCompletedProject` que se ejecuta una sola vez antes del loop. Trade-offs: con MAX_ITERATIONS=8 el peor caso del loop puede tomar 6-8 horas (cada iter requiere lectura holística+beta + reescritura masiva); el snapshot guarda contenido COMPLETO de todos los capítulos en memoria — con 30 caps de 4000 palabras son ~3MB por snapshot, aceptable, pero crash del proceso entre snapshot y restauración pierde el snapshot. La regresión solo dispara cuando la suma combinada cae ≥1.0 (umbral conservador para evitar restaurar por ruido de scoring); caídas más pequeñas se aceptan como parte de la exploración. El target estricto significa que series con `force` o capítulos muy débiles pueden quedarse en loop hasta MAX_ITERATIONS sin aprobar y SIN pulido ortotipográfico final — el usuario debe revisar manualmente desde el dashboard.

Implementación: **(1) Helpers nuevos** — `server/utils/ai-usage.ts` extrae `recordRawAiUsage` (antes inline en `routes.ts:22`, ahora reutilizable sin ciclos de import); `server/utils/series-milestones-extractor.ts` con `extractMilestonesAndThreadsFromGuide({seriesId, seriesGuide, skipIfExists, projectId})` que llama al modelo, parsea JSON con regex de `{...}` y persiste milestones+threads en lote (idempotente por flag `skipIfExists`: si ya hay datos, return temprano con `skipped: true`) y `buildSeriesMilestonesAndThreadsBlock({seriesId, volumeNumber, totalVolumes, isPrequel})` que devuelve un bloque Markdown con tres secciones: hitos OBLIGATORIOS del volumen actual, hitos FUTUROS prohibidos de adelantar, hilos abiertos a continuar/cerrar; retorna `""` si la serie no tiene nada extraído. **(2) Endpoint refactor** (`/api/series/:id/guide/extract`): reescrito para usar el helper en lugar de la lógica inline duplicada (~130 líneas eliminadas). **(3) Auto-extracción tras convert-to-series** (`server/routes.ts:3284-3309` para proyecto, `3715-3741` para reedit): tras generar la `seriesGuide`, lanza `extractMilestonesAndThreadsFromGuide` en **fire-and-forget** (`void (async()=>{...})()`) — la extracción toma ~30s y no debe bloquear la respuesta del endpoint; si el usuario inicia el vol 2 antes de que termine, los volúmenes posteriores la usarán igualmente porque el orchestrator relee en cada generación. **(4) Inyección a agentes** (`server/agents/architect.ts:67-76` input field + `579-596` prompt block; `server/agents/ghostwriter.ts:104-112` + `827-844`): nuevo input opcional `seriesMilestonesAndThreads?: string` renderizado en el system prompt tras el bloque de `seriesUnifiedWorldBible`. **(5) Orchestrator** (`server/orchestrator.ts`): en los **3 scopes** donde se genera capítulos de serie — main (~L1258-1287), resume (~L3026-3045) y qa_rewrite quirúrgica (~L12584-12600) — se hace `dynamic import` de `buildSeriesMilestonesAndThreadsBlock`, se lee `series.totalPlannedBooks` y se computa `isPrequel` (`projectSubtype === "prequel"` o `seriesOrder === 0`), generando `seriesMilestonesBlockStr`. Trade-offs y limitaciones: la auto-extracción fire-and-forget es best-effort sin garantías de finalización; si crashea a mitad (p.ej. tras insertar milestones pero antes de threads), las llamadas posteriores con `skipIfExists=true` saltarán dejando extracción parcial permanente — workaround: existe el endpoint manual `/guide/extract` que el usuario puede llamar con `force` (aún no implementado el flag, pero se puede lanzar tras borrar las filas). El extractor NO usa transacción ni unique constraint a nivel DB, por lo que una llamada concurrente entre auto-extracción y manual puede insertar duplicados (riesgo bajo: el modelo tarda ~30s y rara vez se solapan). Estas mejoras quedan para Fix posteriores si se observan en producción. Solo afecta a series creadas a partir de Fix80; series existentes deben llamar `/guide/extract` manualmente (o usar el botón en la UI) para poblar sus tablas — desde ahí los volúmenes 2+ ya recibirán el bloque inyectado.

- **[Fix77] El bucle Holístico+Beta se repite automáticamente tras la generación hasta que el Beta dé score ≥ 9/10 (flujo desatendido por defecto, v8)**: Petición del usuario: "tras finalizar el libro, repite el proceso Lector Holístico + Lector Beta de forma desatendida hasta que el Beta diga 9+ — y no debe ser necesario marcarlo en el proyecto, debe hacerlo automáticamente por defecto". Hasta Fix76 el método `runAutoHolisticReviewLoop` (`server/orchestrator.ts:7279`) hacía UNA sola pasada paralela de Holístico+Beta, persistía las instrucciones en `pendingEditorialParse` y notificaba al frontend — el autor recibía un manuscrito con score 7-8 y tenía que ir manualmente al dashboard a aplicar los cambios y relanzar la revisión. Además solo corría si `projects.autoHolisticReview === true` (campo con default `false`, opt-in), incompatible con la promesa de "flujo desatendido". Implementación: **(1) Bucle iterativo** (`server/orchestrator.ts:7282+` refactor completo de `runAutoHolisticReviewLoop`): hardcoded `TARGET_BETA_SCORE = 9` y `MAX_ITERATIONS = 3` (sin nuevo flag, sin nuevo schema).
