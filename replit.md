# LitAgents v8

LitAgents orchestrates autonomous AI literary agents to manage the entire novel-writing workflow, from authoring to translation and management.

## Run & Operate

To run the application locally, ensure you have Node.js installed.

```bash
# Install dependencies
npm install

# Run database migrations
npx drizzle-kit push:pg

# Start the development server
npm run dev
```

**Environment Variables:**

- `DATABASE_URL`: Connection string for your PostgreSQL database.
- `DEEPSEEK_API_KEY`: API key for DeepSeek V4-Flash models.
- `FISH_AUDIO_API_KEY`: API key for Fish Audio TTS service.

## Stack

- **Frameworks**: React, Express
- **Runtime**: Node.js
- **Language**: TypeScript
- **ORM**: Drizzle ORM
- **Validation**: Zod
- **Build Tool**: Vite (client), esbuild (server)
- **UI**: shadcn/ui (Radix UI, Tailwind CSS)
- **Routing**: Wouter
- **State Management**: TanStack Query
- **AI Models**: DeepSeek V4-Flash (all agents)

- **[Fix89] Salida del loop Holístico+Beta por "convergencia aceptable" cuando el progreso real existe pero el target dual estricto no se puede alcanzar (v8)**: Queja del usuario tras revisar el log de "El eco del asfalto": "el loop terminó con B=9 H=5 sin aplicar nada y sin ortotipográfica — pero el manuscrito SÍ había mejorado desde el arranque y se ha tirado todo el trabajo". Diagnóstico: el target dual estricto de Fix81 (Beta≥9 AND Holístico≥8) es correcto cuando el cirujano cap-a-cap PUEDE seguir avanzando, pero cuando las únicas críticas restantes del Holístico son estructurales no aplicables (Fix87 las ruta a `pendingAdminActions`), el bucle se queda con 0 instrucciones aplicables iteración tras iteración. Las 3 salidas no-target (`auto_holistic_no_instructions` L7801, `auto_holistic_stalled` L7824, `auto_holistic_max_iter` L7837) persistían las notas sin ejecutar ortotipográfica final, descartando el progreso. Implementación: **(1) Tracking de scores iniciales** (`server/orchestrator.ts:7506-7513`): nuevas variables `initialBetaScore` e `initialHolisticScore` que se setean en la primera iteración con score no-nulo (L7603-7605). Capturan el "punto de partida" para medir progreso acumulado vs delta inter-iteración (que ya existía como `prevBetaScore`/`prevHolisticScore`). **(2) Helper `tryAcceptableConvergenceExit`** (`server/orchestrator.ts:7557-7604`): función local dentro de `runAutoHolisticReviewLoop` que comprueba el criterio de convergencia aceptable — `holisticScore − initialHolisticScore ≥ 2` (Holístico subió ≥+2 desde inicio) Y `betaScore ≥ TARGET_BETA_SCORE − 1` (Beta ≥ 8, estable cerca del target). Si se cumple, restaura `bestSnapshot` (la mejor combinación vista por Fix81), ejecuta `runOrthotypographicPassAndUpdate` y notifica vía callback `onAutoReviewReady`. El log de éxito incluye el delta de Holístico desde inicio y menciona explícitamente que el target dual no se alcanzó porque las críticas restantes son estructurales no aplicables, para que el usuario entienda por qué se ha aceptado SIN clavar B≥9 AND H≥8. **(3) Wiring en las tres salidas no-target**: `if (await tryAcceptableConvergenceExit(...)) return;` se inserta ANTES de `persistAutoReviewResult` en los tres puntos: salida por sin-instrucciones (L7865-7872), salida por estancamiento (L7896-7904) y salida por máximo de iteraciones (L7917-7921). Cada llamada incluye un `reason` distinto para el log. Trade-offs: el umbral `Δholistic ≥ +2` puede ser exigente si el manuscrito ya empezó alto (e.g. H=7→9 cumple, pero H=8→9 no cumple porque solo subió +1). Considerado correcto: cuando arrancamos con H≥8 el target dual ya se cumple en la primera iter y el loop ya sale por la vía normal (L7762 `targetMet`). El criterio Δ+2 es relevante solo cuando arrancamos con H bajo (5-7) y queremos premiar el progreso real. El umbral `betaScore ≥ 8` es deliberadamente más laxo que `TARGET_BETA_SCORE = 9` porque el escenario típico es "Beta ya está alto pero el Holístico es el que ha movido la aguja"; exigir Beta=9 estricto haría inviable la salida en casos donde Beta cae a 8 puntualmente. El helper SIEMPRE intenta restaurar `bestSnapshot` antes de ortotipográfica (no-op si la iter actual ES la mejor, gracias a Fix81 snapshot tracking). Si el snapshot tiene drift estructural (capítulos eliminados desde entonces), se restaura solo el contenido de los que aún existen y se loguea el `missing`. La ortotipográfica final SIEMPRE corre tras una salida de convergencia aceptable — eso era exactamente lo que el usuario perdía.
- **[Fix88] Refuerzo del CONTEXTO DE SERIE inyectado a Holístico y Beta con un "BRIEF OPERATIVO" directivo de qué penalizar y qué no según el vol N de M (v8)**: Queja del usuario: "el Holístico está penalizando que queden hilos abiertos en el vol 2 de 5 como si fuera el último libro, y exige reescribir el clímax — el contexto de serie ya se le pasa pero está siendo ignorado". Diagnóstico: desde Fix58 el helper `buildSeriesContextForReviewers` (`server/utils/series-context-builder.ts`) construye un bloque markdown con `vol N de M`, milestones, hilos heredados y eventos previos, e inyecta ese bloque en el system prompt de ambos lectores. Los system prompts de `holistic-reviewer.ts` y `beta-reader.ts` ya tienen regla 5 ("ajusta tu severidad según vol N/M"), pero en la práctica el modelo seguía aplicando rúbrica de "novela autoconclusiva" en volúmenes intermedios: los párrafos de framing eran descriptivos ("Esta novela es el vol 2 de 5...") y la regla quedaba sepultada al final, sin ser directiva-imperativa. Implementación: **(1) Nuevo bloque "BRIEF OPERATIVO PARA ESTA REVISIÓN"** (`server/utils/series-context-builder.ts:80-119`): se inserta justo después del header `## CONTEXTO DE SERIE` y antes del resto del contenido. El brief usa formato lista corta con tres bullets imperativos: "Estás revisando el VOLUMEN N DE M (...)", "**PENALIZA**: ..." (qué SÍ debe valorar negativamente), "**NO PENALICES**: ..." (qué NO debe penalizar). Los contenidos del brief se diferencian según tres casos: (a) precuela → marco "primer libro cronológico, NO autoconclusiva", penaliza contradicciones con vols posteriores e incoherencias internas, NO penalices hilos abiertos hacia vol 1+; (b) último volumen → penaliza cualquier arco abierto e incoherencias con vols previos, NO penalices elementos nuevos que cierren tramas; (c) volumen intermedio → penaliza incoherencias internas y hitos obligatorios ausentes Y contradicciones con vols previos publicados, NO penalices arcos largos de serie que cierren en vol N+1, hilos heredados abiertos, cliffhanger o ganchos al futuro. **(2) Cuarto bullet inviolable**: en los tres casos el brief incluye explícitamente "**NO EMITAS** instrucciones tipo `tipo:\"estructural\"` que pidan eliminar/fusionar/podar capítulos enteros, mover caps de posición, reescribir el clímax desde cero o reestructurar actos enteros. El sistema NO las puede ejecutar automáticamente (el cirujano trabaja capítulo a capítulo). Si una crítica es estructural, expón el diagnóstico en prosa para que el usuario decida; NO la incluyas en el bloque INSTRUCCIONES_AUTOAPLICABLES". Este refuerzo es complementario a Fix87 — Fix87 actúa como red de seguridad backend (ruta a admin si el modelo igualmente las emite), Fix88 intenta evitar que el modelo las emita siquiera. **(3) Sin cambios en system prompts ni callers**: la firma del helper no cambia, ambos endpoints siguen llamándolo igual, regla 5 de los prompts queda como respaldo. Trade-offs: el brief usa Markdown con negritas (`**PENALIZA**`) y bullets que DeepSeek V4-Flash parsea bien, pero modelos más débiles podrían ignorarlo. No se hace AB testing — se asume que la duplicación de la directiva (brief al inicio del contexto + regla 5 del system prompt) es suficiente. El criterio de "vol intermedio" usa `volumeNumber < totalVolumes`; series con totalPlannedBooks erróneo (= 1 cuando son más) caerían en la rama "último volumen" y penalizarían arcos abiertos legítimos — el usuario tiene `series.totalPlannedBooks` editable para corregirlo. Las precuelas mantienen el framing extendido (Fix68/Fix68b) tras el brief, no en lugar de él. Series sin `series.title` rotas seguirían sin contexto (el helper retorna `undefined` por la guardia `if (!seriesData)`). Los manuscritos ya revisados con el contexto antiguo NO se re-revisan automáticamente — el fix aplica desde la siguiente invocación del Holístico o Beta.
- **[Fix87] Rutar instrucciones estructurales no-aplicables del Holístico/Beta a `pendingAdminActions` ANTES del cirujano cap-a-cap (v8)**: Diagnóstico del proyecto "El eco del asfalto": el loop Fix81 terminó iter 4 con Beta=9, Holístico=5, 0 instrucciones aplicadas, sin ortotipográfica final. Resultado: 0 aplicadas, el loop entra en estancamiento, sale sin ortotipográfica. El usuario veía progreso en Beta pero nunca lograba el cierre. Implementación: **(1) Helper `isMultiChapterStructuralReshape`** (`server/orchestrator.ts:14096-14130`): nueva función paralela a `isStructuralRestructureInstruction` pero que opera sobre el TEXTO COMBINADO de la instrucción del Holístico/Beta (descripcion + instrucciones_correccion + plan_por_capitulo), ANTES de mandarla al cirujano. Cuando `tipo === "estructural"` y `isMultiChapterStructuralReshape(reshapeCorpus)` matchea, la instrucción se pushea a `pendingAdministrative` con `tipo: "structural_restructure"`, el `descripcion` prefijado con `[Estructural caps X, Y, Z]` para visibilidad inmediata, y se hace `continue` saltándose el push al array `valid`. Las instrucciones tipo `puntual`, `eliminar`, `regenerate_chapter`, `global_rename`, `restructure_arc` NO se ven afectadas (no se evalúa la regex sobre ellas). **(3) Persistencia en `pendingAdminActions`** (`server/orchestrator.ts:5609-5640`): el caller `parseEditorialNotesOnly` (que ya manejaba `pendingAdministrative` solo como activity log) ahora filtra los `tipo === "structural_restructure"` y los persiste en `projects.pendingAdminActions` con `type: "structural_restructure"`, `targetChapter: 0` (porque pueden afectar a varios caps o ser globales), `targetLabel` con el descripcion truncado, `source: "holistic-beta-auto-loop"` y un `id` correlativo respetando los existentes. El merge atómico re-lee el proyecto desde BD justo antes de persistir (mismo patrón que Fix40 L13294-13307) para no perder admins añadidas por procesos concurrentes. **(4) Log de aviso reforzado** (`server/orchestrator.ts:5593-5606`): el activity log que ya existía para pendingAdministrative se extiende con un nuevo label "REESTRUCTURACIÓN ESTRUCTURAL (Fix87)" y un párrafo final dirigiendo al usuario a "Acciones administrativas pendientes" en la UI. Trade-offs: las `pendingAdminActions` con `type: "structural_restructure"` NO tienen handler en `applyConfirmedAdminActions` ni en el cirujano del Architect — son meramente informativas; el usuario decide si descartarlas o ejecutarlas manualmente vía herramienta de gestión de capítulos o un futuro endpoint Architect.restructure_arc. La UI ya las muestra como pendientes en la tarjeta de admin actions (Fix40 UI no diferencia por type). El check NO se aplica a `tipo:"puntual"` aunque el `instrucciones_correccion` mencione "elimina este párrafo" porque el cirujano sí puede hacer ediciones puntuales destructivas dentro de un capítulo. El check NO desaparece la información del informe Holístico — el cuerpo del informe (texto libre con el diagnóstico) sigue persistiéndose en `projects.lastHolisticNotes` (Fix82), así que el usuario puede leer el porqué de cada estructural. Si una instrucción genuinamente puntual usa palabras como "elimina la escena del bar" sin mencionar "capítulo", la regex NO matchea (todos los patrones exigen referencia a "cap[ií]tulos?" o sustantivos estructurales claros como "clímax", "acto", "desenlace"). Las instrucciones mal redactadas que matcheen falsamente como estructurales se rutan a admin — pero ese es el comportamiento deseado: si la redacción confunde al matcher, también confundirá al cirujano.

Además, segundo bug latente: la rama `series_writing` del user message del agente (`server/agents/style-guide-generator.ts:496`) concatena `params.seriesIdea` pero el endpoint solo pasaba `seriesDescription` — el system prompt (L362) sí leía la descripción, pero el user message terminaba con solo el título y el total de libros, produciendo guías genéricas desconectadas del libro real. Implementación: **(1) Backend captura error** (`server/routes.ts:3227-3233, 3324-3331`): nueva variable `let guideError: string | null = null` antes del bloque; el catch ahora hace `guideError = err?.message || String(err)` y el log mantiene el `console.error` para diagnóstico. **(2) Doble vía de contexto al modelo** (`server/routes.ts:3268-3284`): el `bookSummary` (título + género + tono + capítulos + premisa + personajes + extractos del primer/último capítulo) se construye igual que antes pero se pasa al agente como `seriesDescription` Y como `seriesIdea` — coherente con la lectura del user message del agente. **(3) Surface en respuesta** (`server/routes.ts:3411-3427`): el JSON de respuesta incluye `guideError`; el `messageParts` añade "ATENCIÓN: la guía de serie NO se generó (msg)" cuando `generateGuide && !guideGenerated && guideError`. **(4) Frontend toast secundario** (`client/src/pages/config.tsx:154-166`): tras el toast de éxito, si `data.guideError` está presente se dispara un segundo `toast` con `variant: "destructive"`, título "Guía de serie NO generada" y descripción que incluye el mensaje del error + indicación de regenerar manualmente desde el taller de guías. Trade-offs: el endpoint sigue devolviendo 200 (la conversión a serie en sí ha tenido éxito; solo la guía falló), porque devolver 5xx haría que el frontend tratase el conjunto como fallido y no se enteraría de que el proyecto SÍ está ya vinculado a la serie. El segundo endpoint `POST /api/reedit-projects/convert-to-series` NO usa try/catch alrededor de `generateStyleGuide`, así que si falla el endpoint entero retorna 500 (loud failure, el frontend muestra error general) — el comportamiento allí es seguro y no se modifica en este fix; si se quiere paridad fina (serie creada + guía fallida sin perder la conversión), habría que envolverlo igual, pero no era la queja del usuario. **Cobertura del endpoint hermano (paridad añadida tras code review)**: `POST /api/reedit-projects/convert-to-series` (`server/routes.ts:3711-3782`) tenía exactamente el mismo problema en dirección opuesta — la generación de la guía NO estaba envuelta en try/catch, así que un fallo del agente reventaba el endpoint con 500 dejando una serie huérfana ya creada en DB sin que el frontend lo supiera. Aplicada la misma envoltura: `reeditGuideGenerated`/`reeditGuideError`, el bloque de Fix80 auto-extract ahora vive DENTRO del try (no tiene sentido extraer hitos de una guía que falló) y la respuesta JSON respeta `guideGenerated: reeditGuideGenerated` (antes era hardcoded `true`) y añade `guideError`. Frontend simétrico en `client/src/pages/reedit-series.tsx:270-280`: tras el toast de "Serie Creada", si `data.guideError` está presente dispara el toast destructivo "Guía de serie NO generada". La auto-extracción de hitos/hilos de Fix80 seguirá saltándose silenciosamente si la guía falla, porque sin `series.seriesGuide` no hay nada que extraer (comportamiento correcto).

## Architecture decisions

- **Autonomous Agent Orchestration**: Uses a modular agent system (`BaseAgent` inheritance) for specialized tasks, managed by a central orchestrator, allowing for complex, multi-step literary workflows.
- **DeepSeek V4-Flash Context Window**: Leverages the 1M token context window of DeepSeek V4-Flash by injecting full previous chapter texts, entire previous volumes (for series), and pseudonym catalogs into agent prompts for enhanced coherence and reduced repetition.
- **Two-Step Editorial Workflow**: Editorial notes are first parsed and previewed (structured JSON output) before application, giving users control over AI-suggested changes and enabling a human-in-the-loop approval process.
- **Robustness and Auto-Recovery**: Includes mechanisms like best-effort buffers for agent outputs, automatic retry logic for failed generations (Architect, word count), persistence of partial progress (KDP pipeline, mid-generation checkpoints), and defensive filters for AI-generated instructions to prevent errors and ensure continuity.
- **Server-Sent Events (SSE) for Background Tasks**: Long-running AI operations (e.g., holistic review, editorial parsing) respond immediately with HTTP 202 and stream updates via SSE, preventing timeouts and keeping the UI responsive. Heartbeats are implemented to maintain connections.

- **Novel Generation**: Orchestrates AI agents for authoring new literary works.

## Gotchas

- **KDP Pipeline Execution**: KDP pipeline runs in the background and persists progress incrementally. Partial failures are tolerated (market marked with `error`, pipeline continues).
- **Architect Timeout**: The Architect agent's phase 2 can take up to 18 minutes for large novels (post-[Fix18] extended schema); the orchestrator's frozen monitor (`HEARTBEAT_TIMEOUT_MS`) is set to 22 minutes, leaving a 4-min safety margin. Phase 1 keeps the default 12-min timeout.
- **Structural Notes Handling**: Editorial notes requesting structural changes (delete/merge chapters) are explicitly *not* auto-applied but logged as administrative actions requiring manual confirmation, preventing accidental data loss or corruption.
- **SSE Connection Stability**: Long-running background processes (holistic review, editorial parsing) rely on SSE. Cloudflare can close idle connections. A heartbeat mechanism and DB persistence for results are implemented as safeguards.
- **Re-running Series Arc Verification**: For standalone projects, `runStandaloneArcCheck` is invoked after `finalizeCompletedProject` to audit arc closure.
- **Narrator Header Leakage**: The Ghostwriter agent has defensive sanitization to prevent meta-referential chapter headers from appearing in the generated prose.
- **DeepSeek `temperature`/`top_p`**: When `thinking` is enabled for DeepSeek models, `temperature` and `top_p` parameters are silently ignored.
